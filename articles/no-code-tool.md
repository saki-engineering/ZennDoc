# ノーコード・ローコードツールの特性

## 「サーバーを意識しない」という言葉の真の意味
さて、ノーコード・ローコードツールではサーバーの存在を開発者が意識しなくていいようにバックエンドの概念が隠蔽されているわけですが、そもそもサーバーは何をしているものなのでしょうか。

我々が普段から慣れ親しんでいるクライアント/サーバーモデルは、高価なサーバーリソースを利用して計算を行いたいクライアントがネットワーク経由でそのような処理リクエストを送り、得られた処理結果も同じネットワーク経由で返却したいという考え方が発端となっています。
この考えの前提として1台のコンピューターのCPU処理時間を細かく分割し短時間で利用ユーザーを切り替えさせることによって、あたかも複数ユーザーで同時に1台のコンピューターを使っているように見せかけるというタイムシェアリング(TSS)[^1]が存在します。
その後、このタイムシェアリング機の資源を多数のユーザーで分け合うという活動をネットワーク越しに行えるようにしようという発想を元にARPANETが作られ、これが今日のインターネットの礎となっています。
[^1]: 1960年代での出来事なので、ここでいうコンピューターというのは主にメインフレームのことです

このように、サーバーという存在の本質は「1つの機体のリソースを大人数で分け合い共有する」というモデルにあります。
高価なサーバーを複数のクライアントで共有し一人当たりの処理コストを小さくすることによって、誰しもがコンピューターの恩恵に預かることができるようになったのです。

サーバーによるリソース共有の考え方が発展していくと、今度は
- 1台のサーバーリソースのどこを全クライアントで共有するのか
- 複数のクライアントの処理内容が混ざってしまわないように、適切にリソースを分離・分割できるのか
という点が新たな課題として上がってきます。

## リソースを適切に共有することの難しさ
1つのリソースを複数のEntityで分割・共有するという考え方が活きているは、何もクライアント/サーバーモデルだけではありません。実例をいくつか挙げてみたいと思います。

まずは仮想マシンです。
これはホストマシンが持つCPU/メモリ/ディスク/NICといった物理的なハードウェアをハイパーバイザによって仮想化し、その上に複数個のVMを起動させるというやり方が取られます。
これは言い換えると「ハイパーバイザを使うことによって、ホストマシンの物理的なハードウェアを複数のVMで共有する」というモデルです。

次にコンテナです。
これはホストマシンのOSをコンテナランタイムによって仮想化し、その上に複数個のコンテナを起動させるというやり方を取ります。
言い換えると「コンテナランタイムを使うことによって、ホストマシンのOSカーネル機能を複数のコンテナで共有する」というモデルです。

インフラに近い具体例を2つあげたので、次は少し毛色を変えてインターネットブラウザに関する例を挙げてみたいと思います。
ホストマシン上にブラウザアプリケーションをインストールすることによってインターネット上にある様々なサイトを閲覧することができるようになるわけですが、このとき異なるドメインのサイト描画には異なるOSプロセスが用いられるようになっています。
つまり、「ブラウザアプリを使うことによって、ホストマシンのリソースを複数のサイト描画タブで共有する」というモデルです。

このように、一つのリソースをいくつかの仮想的な空間で分割して用いる技法は世の中に数多く存在します。
しかしこれらの技術において問題になるのは、この仮想的な分割が果たして正しく機能しているかどうかという点です。
分割・隔離が甘いとそれはセキュリティ脆弱性につながります。
例えばかつてruncに見つかったCVE-2019-5736[^2]の脆弱性は、コンテナランタイムのファイルディスクリプタ扱いの不備を利用してホストOSのroot権限を奪取するというものでした。ホストOSのroot権限を足がかりにして同じホストマシン上に乗っている他のコンテナへの侵入侵害も理論上可能であるということで、NISTの10点満点のスコアで8.6(High)を叩き出すほど高く警戒されました。
また、2024年に話題になったLeaky Vesselsの一連の脆弱性は、コンテナ技術によって隔離されていたはずのリソースにアクセスできてしまうということで世間を震撼させました。
[^2]: https://nvd.nist.gov/vuln/detail/cve-2019-5736

このようにコンテナエスケープに関するCVEは後をたちません。一つのリソースを複数のContextで適切に共有できるようにする隔離技術の実現はとても難易度が高いということがお分かりいただけるのではないでしょうか。

## フロントエンドとバックエンドの結合度
このように、サーバーというのは「複数のクライアントでリソースを共有することによって、一人当たりの処理コストを小さくして、パフォーマンスを向上・最適化する」という考えのもとに作られたものです。
しかしこのリソース共有の考え方は、分離・隔離が不十分だとセキュリティ脆弱性に繋がりかねない諸刃の剣です。
ここにおいて、パフォーマンス効率とセキュリティの堅牢さというのはある種のトレードオフが成り立っています。

これを踏まえた上で、ノーコード・ローコードツールがどのような特性を持つのかをみていきたいと思います。
まず、ノーコード・ローコードツールはサーバーの概念が徹底的に隠蔽されています。とあるリクエストに対してどのような処理をしたいのかということをGUIベースで指定することはできても、リクエスト横断で行うリソース共有ロジックを書くことはできません。
これはサーバーの「リソース共有によるパフォーマンス最適化」という役割を隠蔽しているからであり、ゆえに出せる性能の上限はカスタム開発と比べて明確に低くなります。

また、サーバーが持つリソース共有の考え方を徹底的に封じられているということは、一つのクライアントリクエストごとにコンテキストが厳しく分離されているということです。
例えばPower Automateは異なるフロー間でStateを共有する術はありません。また、Power Pagesのサーバーロジックも、リクエストContextを横断してStateを保持・共有することは絶対にできないようになってます。

さらに、このバックエンドでのコンテキスト分離を脅かすような入力ができないように、サービスで提供される機能についてもある種の制限を受けることになります。
その制限の度合いはサービス種別に応じて異なります。例えば以下のサービスについて考えてみましょう。
- PaaS (Platform as a Service)
- FaaS (Function as a Service)
- BaaS (Backend as a Service)
- aPaaS (Application Platform as a Service)
- SaaS (Software as a Service)

PaaS, FaaS, BaaSに関してはバックエンドの処理内容に関わらず、どんな内容のフロントエンドも作ることができます。
Backend as a Serviceはそもそもフロントエンドの提供はスコープ外、FaaSはMVCモデルのようなサーバーを提供するのに不向きだというそもそも論はあるのですが、開発者がバックエンドのことを意識せずに(他サービスを使いながら)好きにフロントエンドを構成することができるという点についてはこの3つは共通しています。
表現を変えると、これら3つのサービスはフロントエンドとバックエンドが疎結合なのです。

それに対してaPaaS, SaaSはフロントエンドとバックエンドが密結合です。
aPaaSはある程度開発者の自由に画面・UXを作り込むことができますが、これで構成した画面アプリケーションのバックエンドはそのaPaaS上でしかホストすることができません。
SaaSに至ってはフロントエンド・バックエンドともに開発者が手を入れることはできません。SaaS提供側が用意したフロント・バックエンドがセットになった密結合アプリケーションをそのまま使うという形になります。
フロントエンドとバックエンドが密結合であると、フロントエンドで悪意のある入力をされるとその悪影響がバックエンドに波及しやすいです。そのため、双方で機能を制限することでセキュリティを担保しようという設計思想になります。
例えばPower PagesではDataverseのJOINを実行することはできません。





# ドラフト
ノーコード・ローコードツールという言葉の定義の通り、ユーザーにはなるべくコードロジックを欠かせたくないという思想があるので、**サーバーサイドロジックおよびサーバーの存在は徹底的に隠蔽される**傾向にある。
例えばPower Pagesとか考えると早い。ConfigやFlagで挙動を変えさせることはできても、その項目にないものに対しては手出しができない

サーバーの存在が隠蔽されているという思想が浮き出ている例は他にもある。
そもそもローコード・ノーコードツールの前提として、プログラムやシステム構築の素養がない一般ワーカーにもシステムやツール開発ができるようにするというものがある。
そのため、基本的には機能要件さえ満たせればいいという思想になっている。


ユーザーリクエスト間でどれだけContextやメモリが分離されているかでみるとまた違った分類になる。
フロントエンドの触れ口が広いと、バックエンドの分離は厳しくしないとセキュリティが不味くなる。だからpower pagesのバックエンドは厳しい。
